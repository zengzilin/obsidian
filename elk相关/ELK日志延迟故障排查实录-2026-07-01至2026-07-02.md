# ELK日志延迟故障排查实录

## 基本信息

- 排查时间: 2026-07-01 至 2026-07-02
- 故障现象: Kibana / ELK 中应用日志展示明显延迟
- 日志链路: `Filebeat -> Kafka -> Logstash -> Elasticsearch -> Kibana`
- 相关 Topic: `tiqmo-svrlog`
- 原消费组: `logstash-svrlog-k8s`
- 新消费组: `logstash-svrlog-k8s-new`
- 关键 Pipeline: `tiqmo-svc-logs`

## 最终结论

这次日志展示延迟不是单一问题，而是分阶段暴露出的链路瓶颈：

1. 最开始的直接问题是 `Kafka lag` 很大，说明 `Logstash` 消费速度赶不上 `Filebeat/Kafka` 写入速度。
2. `tiqmo-svrlog` 初始只有 `3` 个 partition，消费并行度上限过低，导致 4 个 Logstash 也无法充分利用。
3. 把 Topic 扩到 `6` 个 partition 之后，并行度问题有所缓解，但延迟没有彻底消失。
4. 进一步排查发现真正长期瓶颈在 `Logstash -> Elasticsearch` 输出端，具体表现为 ES 单节点写入热点，导致 Logstash output 几乎打满，Kafka 持续积压。
5. 即使换了新的 `group_id`，新消费组依然快速形成新的 lag，说明问题不再是旧 offset，而是当前实时吞吐不足。

一句话总结：

> 这次 ELK 日志延迟的根因，是 Kafka 积压和 Elasticsearch 写入热点叠加导致的，其中最终主瓶颈在 Elasticsearch 写入侧，而不是 Kibana 展示层。

---

## 排查过程

### 1. 先看 Elasticsearch 集群总体状态

最开始从 Kibana 的 Elasticsearch Overview 页面观察到：

- 集群状态是 `Green`
- `Indexing Latency` 大多只有 `0.1 - 0.3 ms`
- `Search Latency` 大多只有几毫秒
- JVM Heap 没有明显异常

初步判断：

- 不是 Elasticsearch 集群整体不可用
- 也不像是 Kibana 查询层本身慢
- 需要继续往 `Kafka -> Logstash -> ES` 链路前面查

---

### 2. 检查 Kafka 消费组 lag

执行命令：

```bash
kafka-consumer-groups.sh --bootstrap-server 127.0.0.1:9092 --describe --group logstash-svrlog-k8s
```

当时的关键输出：

- partition 0: lag `57,233,973`
- partition 1: lag `50,372,301`
- partition 2: lag `49,560,144`
- 总 lag 约 `157,166,418`

结论：

- 日志不是“偶发晚几秒”
- 而是已经在 Kafka 中形成了大规模积压
- 说明 `Logstash` 消费吞吐显著低于 Kafka 生产速度

随后连续观测 lag 趋势，发现 lag 还在继续上涨，说明系统不是在追平，而是在继续失血。

---

### 3. 检查 Logstash pipeline 运行状态

执行命令：

```bash
curl -s http://127.0.0.1:9600/_node/stats/pipelines?pretty
```

重点观察到两类 pipeline 现象：

#### `tiqmo-ingress-nginx`

- `pipeline.workers = 1`
- `worker_concurrency = 1.0`
- `worker_utilization = 100%`
- `queue_backpressure ≈ 0.98`
- `output.elasticsearch.worker_utilization ≈ 97.88%`

结论：

- 这条 pipeline 的唯一 worker 已经打满
- Kafka input 在等待 pipeline 空位
- 真正瓶颈不在 filter，而在 `elasticsearch` output

#### `tiqmo-svc-logs`

后续进一步拿到这条和 `svrlog` 相关的 pipeline stats，关键值如下：

- `pipeline.workers = 12`
- `pipeline.batch_size = 500`
- `pipeline.batch_delay = 5`
- `worker_concurrency = 12.0`
- `worker_utilization = 100%`
- `queue_backpressure = 0.8857`
- `output.elasticsearch.worker_utilization = 98.8%`
- `output_throughput.current ≈ 3073/s`
- `grok.worker_utilization ≈ 0.8%`

结论：

- Filter 不是主瓶颈
- Logstash 的 pipeline worker 几乎都在等 ES output
- 当前延迟本质上是 `Logstash -> Elasticsearch` 吞吐不足，导致 Kafka lag 无法压下去

---

### 4. 检查 Kafka Topic 分区数

执行命令：

```bash
kafka-topics.sh --bootstrap-server 10.21.104.13:9092 --describe --topic tiqmo-svrlog
```

最初结果：

- `PartitionCount: 3`

而当时环境已经扩到了 `4` 个 Logstash。

结论：

- 同一个 consumer group 的有效并行度是：

```text
min(Topic 分区数, Logstash 实例数 x consumer_threads)
```

- 由于 Topic 只有 `3` 个 partition，所以即使有 `4` 个 Logstash，也最多只有 `3` 个活跃消费者
- 第 4 个 Logstash 基本闲置

---

### 5. 扩容 Kafka Topic 分区

执行命令：

```bash
kafka-topics.sh --bootstrap-server 10.21.104.13:9092 --alter --topic tiqmo-svrlog --partitions 6
```

扩容后确认：

- `PartitionCount: 6`

同时将 Logstash Kafka input 调整为：

```ruby
consumer_threads => 2
```

此时变为：

- `4` 个 Logstash
- 每个 `2` 个 consumer thread
- 总线程数 `8`
- Topic 分区数 `6`

理论上已经足够覆盖所有 partition。

结论：

- Kafka 并行度限制问题被部分解决
- 但旧 backlog 不会自动迁移到新分区
- 原来堆积在 `0/1/2` 分区中的历史消息仍然留在老分区

---

### 6. 观察扩分区后的消费情况

扩分区后再次查看消费组：

- 新分区 `3/4/5` 开始有消费者接管
- 老分区 `0/1/2` 依然保留大规模历史 lag

之后发现即使是新分区，也逐步出现了千万级 lag：

- partition 3: `12,252,686`
- partition 4: `10,004,525`
- partition 5: `9,713,019`

这说明：

- 扩分区只是放开了消费并行上限
- 但链路的总处理吞吐仍然小于实时写入速度
- 所以新流量也开始继续积压

---

### 7. 切换新的 Kafka group_id 验证

为了排除“旧消费组历史 backlog 干扰”，创建了新的消费组：

- `logstash-svrlog-k8s-new`

再次执行：

```bash
kafka-consumer-groups.sh --bootstrap-server 10.21.104.13:9092 --describe --group logstash-svrlog-k8s-new
```

关键结果：

- partition 0: lag `6,280,894`
- partition 1: lag `6,313,860`
- partition 2: lag `6,229,908`
- partition 3: lag `8,225,480`
- partition 4: lag `6,238,642`
- partition 5: lag `8,149,373`
- 总 lag 约 `41,437,?` 万级别，仍然很大

结论：

- 新 group 也很快形成 lag
- 说明问题不是旧 offset
- 而是当前实时消费和写入能力本身不够

---

### 8. 检查 Elasticsearch write 线程池

执行命令：

```http
GET _cat/thread_pool/write?v
```

不同阶段分别观察到热点节点：

#### 一次观测结果

- `elasticsearch03 write active=12 queue=277`
- `elasticsearch01 queue=0`
- `elasticsearch02 queue=0`

#### 另一次观测结果

- `elasticsearch02 write active=12 queue=335`
- `elasticsearch03 write active=4 queue=0`
- `elasticsearch01 write active=0 queue=0`

结论：

- 问题不是整个 ES 集群都扛不住
- 而是写入大量集中到单个节点
- 这个热点节点上的 write queue 堆积，拖慢了 Logstash output

---

### 9. 检查 Elasticsearch 节点 stats

进一步查看：

```http
GET _nodes/stats/thread_pool,indexing_pressure,indices/indexing?pretty
```

关键现象：

- `rejected = 0`
- `indexing_pressure` 没有达到限制
- `elasticsearch02` / `elasticsearch03` 上出现较明显的 `write` 活跃和队列
- `elasticsearch01` 资源更大，但未充分承担热点写入

节点资源差异：

- `elasticsearch01`: `24 CPU / 73GB`
- `elasticsearch02`: `12 CPU / 50GB`
- `elasticsearch03`: `12 CPU / 50GB`

结论：

- 不是 ES 全局拒绝写入
- 而是当前写主分片分布不均，热点压在较小节点上

---

### 10. 检查 data stream 和分片分布

执行：

```http
GET _data_stream/*svrlog*
GET _cat/shards/*svrlog*?v&s=index,prirep,node
```

得到的关键结论：

- 当前各个 `svrlog` data stream 基本都是 `3` 个 primary shard，并不是单分片导致的
- 但当前 write index 的主分片分布并不均匀

典型现象：

#### `logs-svrlog-account`

当前写索引：

- `.ds-logs-svrlog-account-2026.06.30-000216`

其中两个 primary shard 落在：

- `elasticsearch02`

这会导致写入更集中到 `elasticsearch02`

#### `logs-svrlog-wallet`

当前写索引：

- `.ds-logs-svrlog-wallet-2026.07.01-001820`

虽然三个 primary 分布到三台节点，但 shard 大小不均：

- es01: `34.3GB`
- es02: `47.7GB`
- es03: `34.6GB`

这说明写入热点和 merge 压力并不均衡。

最终结论：

- Kafka lag 只是表象
- Logstash output 打满是中间现象
- Elasticsearch 热写分片落点不均，才是当前长期瓶颈

---

## 中间尝试和结论修正

### 1. 是否只需要重启 Logstash

结论：不行。

- 重启可以触发 consumer rebalance
- 但不能清理 Kafka backlog
- 也不能解决 ES 写入热点

正确做法：

- 如需重启，只能滚动重启 1 个 Pod
- 不能 4 个一起重启

### 2. 是否只需要增加 Logstash 数量

结论：也不够。

- Topic 只有 `3` partition 时，增加到 `4` 个 Logstash 没意义
- Topic 扩到 `6` partition 后，并行度问题缓解，但总吞吐瓶颈还在

### 3. 是否只需要换新的 group_id

结论：也不够。

- 新的 group_id 只能绕开旧 offset
- 不能提升当前处理能力
- 新 group 很快又形成新的 lag

---

## 本次排查得到的最终判断

### 直接原因

- Kafka 中出现了持续增长的 lag
- Logstash pipeline 的 `worker_utilization` 和 `output.elasticsearch.worker_utilization` 长时间接近 `100%`

### 深层原因

- Kafka 初始 partition 太少，限制了消费并行度
- Elasticsearch 当前 write index 主分片分布不均
- 热点主分片更多落在 `elasticsearch02` / `elasticsearch03`
- `elasticsearch01` 资源更大，但未承担足够热点写入

### 因果链

```text
Kafka 分区过少 / 历史 backlog
    -> Logstash 消费追不上
    -> 扩分区后并行度提升，但仍然被 ES 写入热点限制
    -> Logstash output 打满
    -> Kafka lag 继续增长
    -> Kibana 日志展示延迟
```

---

## 推荐处理方案

### 立即措施

1. Logstash 先使用保守但稳定的并发配置：

```text
consumer_threads = 2
pipeline.workers = 8
pipeline.batch.size = 250
pipeline.batch.delay = 5
queue.type = memory
```

2. 不要继续盲目增加 `consumer_threads` 或 `pipeline.workers`
3. 不要同时保留旧 group 和新 group 一起消费同一个 Topic
4. 只允许滚动重启 Logstash，不允许全量重启

### 缓解 ES 热点

1. 手动 rollover 热点 data stream：

```http
POST /logs-svrlog-wallet/_rollover/
POST /logs-svrlog-account/_rollover/
```

2. 对热点分片执行单次迁移，例如把热点主分片从 `elasticsearch03` 或 `elasticsearch02` 挪到 `elasticsearch01`
3. 一次只迁 1 个主分片，观察 write queue，再决定下一个

### 长期治理

1. 调整热点 data stream 的模板，让未来 backing index 更偏向 `elasticsearch01`
2. 检查并优化 ILM rollover 条件，让热点索引更早切换
3. 尽量统一 3 台 Elasticsearch 节点规格，避免一台大两台小导致热点不均
4. 继续观察：

```bash
kafka-consumer-groups.sh --describe --group <group>
curl -s http://127.0.0.1:9600/_node/stats/pipelines?pretty
GET _cat/thread_pool/write?v
GET _cat/shards/*svrlog*?v&s=index,prirep,node
```

---

## 标准排查顺序沉淀

以后再遇到“ELK 日志展示延迟”，建议按下面顺序查：

1. 先看 Kibana / ES Overview，判断是不是 ES 集群整体不可用
2. 查 Kafka consumer group lag，确认是不是链路积压
3. 查 Logstash pipeline stats，区分是 filter 慢还是 output 慢
4. 查 Topic partition 数和 consumer 实际分配
5. 查 ES `write` 线程池和 `indexing_pressure`
6. 查 data stream 当前 write index 的主分片落点
7. 再决定是调 Kafka、调 Logstash，还是做 ES 分片和热点治理

---

## 额外注意事项

1. 本次排查过程中配置中曾出现 Elasticsearch 明文密码，后续需要立即轮换，并改为环境变量或 Logstash keystore。
2. 如果新 group lag 接近 `0`，但 Kibana 依旧显示延迟，还需要额外排查 `@timestamp`、`event.ingested` 和时区问题。
3. `auto_offset_reset => "latest"` 不能解决已有 lag，只会影响无已提交 offset 的新消费者从哪里开始消费。

---

## 结论摘要

本次故障不是 Kibana 页面问题，也不是单个参数配置问题，而是一次典型的链路型性能故障：

- Kafka 层有积压
- Logstash 层有反压
- Elasticsearch 层有单节点写入热点

真正要解决延迟，必须按链路视角同时治理 Kafka 并行度、Logstash 输出能力和 Elasticsearch 写分片落点。
